# 如何提升RAG的召回率和准确率？

这是一个系统性问题，需要对整条 RAG 管线优化。答题顺序是**先归因、再优化**：用分层指标定位瓶颈，避免在不存在的瓶颈上叠复杂度。

**默认排查顺序：** 解析与分块 → 混合召回与精排 → 查询改写、迭代检索等增量手段。依据是：上游错误会让下游指标不可信（解析坏了，Recall@K 就是脏的），且下游优化补不回上游损失（证据被切碎，重排也无物可排）；增量手段延迟与不确定性最高。**若指标显示瓶颈在别处，按证据调整，不照搬顺序**——顺序决定先查哪里，指标决定改哪里。

## 先定位瓶颈

| 层 | 指标 | 瓶颈表现 |
|---|---|---|
| 解析 | 解析成功率、表格还原率 | 扫描件丢字、双栏 PDF 阅读顺序错乱 |
| 分块 | 抽检块内信息完整性 | 证据被切在边界，主体与条件分到两块 |
| 嵌入与召回 | Recall@K、MRR、Hit Rate | 正确文档根本没进候选 |
| 重排 | NDCG@N、Context Precision | 证据在候选里但排在 Top-N 之外 |
| 生成 | Faithfulness、Answer Correctness | 给了正确证据仍答错、编造或忽略否定条件 |

- **定位方法：** 把正确证据直接塞给模型，仍答错就查生成与上下文组织；答对了，再看是候选覆盖不足（Recall@K 低）还是排序不对（NDCG 低）。

## 数据与解析

- 解析质量是地基：扫描件、双栏 PDF、表格、公式最容易出错，阅读顺序错乱会直接毁掉后续分块与检索。
- 图片用兼容的图文 embedding 做跨模态检索，或 OCR/VLM 抽文字、生成图说后进入文本库；图说需核验并保留原图来源。
- 入库时带来源、章节、版本、生效时间与权限等元数据，供过滤和引用。→ [[04-多源异构数据如何解析和处理]]

## 优化分块策略（Chunking Strategy）

- 块太小丢上下文，块太大向量被稀释、噪声增多；按文档类型和查询模式调整大小与重叠。
- 保留主体、条件、数字、单位及来源，避免证据在边界处断裂。
- 比较结构、递归、语义分块，不默认更复杂就更好。
- **父子块（small-to-big）：** 用小粒度块检索提高命中精度，命中后回溯父块喂给 LLM，兼顾「检索准」与「上下文全」。
- **Contextual Retrieval：** 索引前让模型为每块生成「这段在全文中的位置与主题」前缀再编码，缓解块脱离全局语境；收益需实测。→ [[05-文本如何分块、分块策略和优化方法]]

## 优化嵌入模型（Embedding Model）

- 选择适合目标领域和语言的模型（如 BGE、E5 等），用自有数据评测，不能只看模型名称或通用榜单排名。
- 必要时做领域微调，使用查询、正例和负例，注意假负例及训练测试数据泄漏。
- 遵循模型输入与距离约定，检查截断；换模型后通常需要重新编码文档并更新索引。
- 向量是有损压缩，型号、错误码、否定、条件数字等词面细节容易丢失，靠混合检索与元数据过滤弥补。

## 混合检索与多路召回

- 同时使用 BM25 与向量召回，通过 RRF 或加权融合。两者失效场景不重叠：BM25 漏同义改写，向量漏未登录词与精确 ID。
- 按需求增加多向量或图检索，评估新增证据、噪声、延迟和成本。详见 [[02-RAG有几种召回方式、一般设置几路召回]]。

## 引入重排序模型（Re-ranker）

- **问题：** 候选中已有证据，但排序靠后，或主题相关却无助于回答的片段排名靠前。
- **方案：** 对召回候选做更精细的相关性打分，再选 Top-N 给 LLM。Cross-Encoder 是常见方案，也可使用其他重排模型或 LLM。
- **作用与边界：** 只能改善排序，不能补回未召回的证据；长候选截断也会丢失信息。候选 100、最终 5 等数字只是实验配置，需按效果与成本调整。
- 分数跨 query 不可比，用作阈值过滤前需要校准，否则部分 query 会被整体过滤掉。
- 换重排模型无需重建索引（无状态打分），换嵌入模型则必须全量重编码。

## 查询扩展与改写（Query Expansion/Rewrite）

- **HyDE（Hypothetical Document Embeddings）：** 先生成假设文档，再编码检索真实资料。假设可能有错，不能直接作为事实证据，可与原问题检索融合并评估是否带偏。
- **多查询检索：** 生成互补问法并行检索，合并去重；注意额外成本与意图漂移。
- **查询改写：** 根据已知会话补全指代，保留实体、时间、数字和否定条件。信息不足就澄清，不能凭空增加用户需求。

## 上下文组织（压缩与排序）

- 多路召回结果先去重，常出现同一块的近重复片段。
- 按相关性排序，最相关的证据放在首尾：长上下文中段容易被模型忽略。
- 压缩：抽取相关句或裁剪噪声以降低输入成本；保留数字、单位、否定、例外条件与引用映射。摘要也可能出错，需比较压缩前后的证据覆盖与答案质量。
- 证据冲突时不替模型做选择，要求指出矛盾并标注各处出处。

## 生成层约束

- Prompt 限定只依据给定资料回答，要求给出引用编号；资料不足时明确说明，不凭常识补全。
- 用结构化输出约束格式，便于校验引用是否落在给定资料范围内，也便于下游使用。

## 查询路由、分解与迭代检索

- **查询路由：** 按事实问答、跨文档对比、统计或闲聊，选择合适策略。
- **查询分解：** 把复杂问题拆成子问题，再汇总证据；有依赖的子问题需按顺序处理。
- **迭代检索 / 自我反思：** 根据证据缺口补检索或重写查询，设置轮数、时间和 token 上限。Self-RAG 偏向检索与生成自评，CRAG 偏向检索质量评估和纠正，不能简单混为同一种流程。

## 元数据过滤

- 为文档块添加来源、产品、版本、有效时间、章节和权限等信息。
- 过滤条件应来自问题或业务要求，创建时间不等于生效时间；错误过滤会漏检，ANN 后过滤还可能导致不足 K 条。
- 所有召回路及父块扩展都需保持权限约束，不能为了补足结果而放宽授权。

> [!question] 面试追问
> **Q：HyDE 先造「假设答案」去检索，假设偏了会不会带偏召回？如何规避？**
> **A：** 会。可保留原查询检索，与 HyDE 结果融合后重排，重点检查实体与条件漂移；是否有效仍需评测，不能保证重排一定纠偏。
>
> **Q：嵌入模型和重排序模型都在算相关性，为什么两个都要？**
> **A：** 独立编码便于预计算和大规模粗筛；Cross-Encoder 联合处理查询与文档，适合少量候选精排，通常更贵。是否组合由效果和预算决定。
>
> **Q：优化时先调检索还是先调生成（Prompt）？为什么？**
> **A：** 先归因。直接提供正确证据后仍答错，就检查生成与上下文组织；证据根本没召回，再检查解析、分块和检索。不要机械地总先调某一环。
>
> **Q：分块大小怎么定？**
> **A：** 没有标准值，用自有评测集做网格实验；优先改结构（标题层级切分、父子块），而不是死磕 size 与 overlap。
>
> **Q：这些优化怎么取舍，都要上吗？**
> **A：** 不用。每加一层都要问指标增量与延迟、成本增量是否划算；先做归因后的高 ROI 项，用评测集验证，不凭榜单或直觉。
>
> **Q：带图片的多模态内容怎么纳入召回？**
> **A：** 用兼容的图文 embedding 做跨模态检索，或用 OCR/VLM 抽文字、生成图说后进入文本库。任意图文向量不能混用；图说需核验并保留原图来源，成本按实际链路比较。→ [[04-多源异构数据如何解析和处理]]
